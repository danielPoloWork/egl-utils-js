## The Version PR had not opened, and that is a documented failure

`release-version.yml` pushed `changeset-release/main` with a correct, complete bump — and
opened no PR. That is exactly the case `docs/workflow/release.md` records: opening it needs
**Settings → Actions → General → "Allow GitHub Actions to create and approve pull
requests"**, and the workflow's `pull-requests: write` permission is necessary but not
sufficient because the repository toggle overrides it.

The documented recovery is to open the PR by hand from the already-pushed branch, which is
what happened here — no work was lost, and the prose commit rides the same branch. Worth
noting that the note in `release.md` was written for roadmap 8.1 and has now paid for itself
twice; the setting is still off, so the next release will need the same manual step unless
the owner flips it.

## What the release actually contains

Two pending minors — 18.2's global artifact and 18.3's CDN fields — so changesets computed
**1.1.0**, which is the version the README's no-bundler snippets have been pinning since
18.4. That loose end closes itself when this ships.

The framing the notes lead with is *"the plain HTML page becomes a first-class consumer"*
rather than a list of five roadmap items, because that is what a consumer reading a release
page needs to know. The five items are one capability from the outside.

**Purely additive, and the notes say so early** — the `exports` map is byte-for-byte
identical, a bundler consumer re-bundles to the same graph, `sideEffects: false` holds and
runtime dependencies stay zero. A reader who bundles should be able to stop after that
paragraph.

Both prose files carry the **measured transfer table**, which is unusual for release notes
and earns its place: it is the only thing that answers "which route should I use", and its
headline — `/bootstrap` costs 31.28 kB over 7 requests where the whole artifact costs
31.51 kB over 1 — is advice, not trivia.

## The version bump moved two of the eleven routes

Worth recording, because it will happen at every release and looks alarming the first time.
Running `check:transfer` after the bump reported **`root` −12 B and `artifact` −98 B**, with
the other nine byte-identical. Those two are exactly the routes that carry the `VERSION`
string: changing `1.0.0` to `1.1.0` is one character, and brotli is sensitive enough that the
compression stream shifts around it — more in the artifact, which is one 114 kB file, than in
a small chunk.

So the numbers in the notes were re-measured after the bump rather than copied from 18.5, and
the two declared baselines were re-pinned. Both mattered: the tables in the release notes and
the README would otherwise have shipped a figure the project's own gate reports as stale, in
the release whose selling point is that those figures are measured. `transfer-budgets.js` now
says to expect this at each release, so the next person sees a documented consequence instead
of a mystery.

The historical records — the 18.5 journal, ADR-0061, spec 05 — keep the figures they were
written with. They were true when measured, and re-editing dated records to match today is
how a project loses the ability to say what it knew and when.

## One thing stated rather than buried

The notes say plainly that the transfer figures are **larger** than the per-function budgets
quoted in the README, and why: those measure what a bundler ships after tree-shaking, a
static page downloads whole files. Leaving a reader to discover two different numbers for
the same entry and guess which is wrong would be worse than the paragraph it costs.

## How the next session resumes

1. **The maintainer merges the Version PR.** Merging publishes nothing.
2. The agent then tags: `git tag -a v1.1.0` and pushes it, which makes `release.yml` draft
   the GitHub Release from `docs/releases/v1.1.0.md`.
3. **The maintainer publishes** the GitHub Release, then dispatches the **publish** workflow
   — once with `dry-run` checked to see what would ship, then again unchecked.
4. Only after the npm publish do the README's `@1.1.0` CDN URLs resolve on jsDelivr and
   unpkg. Until then they are correct and not yet live, which is the one thing to check
   first if someone reports them 404-ing.
5. After that, M19–M21 are the provisional waves (ADR-0046), each owing its own spec before
   implementation; execution order is the owner's call.
