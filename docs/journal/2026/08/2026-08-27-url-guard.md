# 2026-08-27 — A URL is not text (23.1)

## What got done

- **`safeUrl`** on `egl-utils-js/sanitize` — spec 09 F126: parse with `new URL()`, then look the
  protocol up in an allow-list. No regular expression sees the input.
- **Seven builder call sites routed through it** (F127), a refusal that leaves the element standing,
  and `data-egl-refused-url` so it is findable.
- **[ADR-0084](../../adr/0084-a-url-is-not-text.md)**, the **threat-model boundary and its STRIDE
  pass**, **ADR-0041's 25 kB `/bootstrap` clause amended to 25.5 kB** with the arithmetic, and the
  call-site count corrected from eight to seven.
- 66 example tests, two of them property tests; `url-guard.js` at **100% lines and branches**;
  3 413 unit tests green.

## The gap, in one sentence

Escaping protects a record's **content**. A record's **URL** is an instruction, and no escape in
this library ever touched it.

```js
bsListGroup([{ content: 'Ada', href: record.homepage }]);
// record.homepage === 'javascript:fetch("/api/keys").then(send)'
```

Seven call sites did that. And the threat model described this boundary's mitigation as *"they
render exactly what they receive"* — which, for an `href`, is not a mitigation. That sentence was
the finding.

## Parse, then decide — and the row that proves it

Every hand-rolled version of this check inspects the string. All of them are wrong in the same four
ways, because the URL grammar removes tabs and newlines *inside* a scheme, strips leading control
characters, lower-cases the scheme, and treats a percent-encoded colon as an ordinary path
character.

| Input | `startsWith('javascript:')` | This guard |
|---|---|---|
| `JaVaScRiPt:alert(1)` | passes | **refused** |
| `java\tscript:alert(1)` | passes | **refused** |
| `\0javascript:alert(1)` | passes | **refused** |
| `%6a%61%76%61script:x` | refused | **allowed** |

The last row is the one I care about most. It is *not* a scheme — the grammar does not decode escapes
in the scheme position, so a browser resolves it as a path — and refusing it would have broken a
legitimate filename while protecting nothing. Over-refusing is a bug too, and only the parser knows
which is which.

Every expectation in the suite was **run against the engine before it was written down**. Two of
them surprised me:

- `''` and `'   '` resolve to the *probe base*, so a guard that only read the parsed protocol would
  have called them `https:` and allowed them. The empty check is load-bearing, not decorative.
- `'http://['` and `'https://'` **throw** rather than resolving, because a value carrying a scheme
  ignores the base. The `catch` is reachable, and my first comment claiming otherwise was wrong.

## Three decisions worth their own lines

**It answers rather than throwing.** A builder rendering fifty records cannot let one hostile field
discard the other forty-nine, so a refusal is `null`. A security check that throws on hostile input
has moved the failure, not removed it — and the property suite asserts totality over 5 000 generated
strings, including an alphabet built from the corpus payloads themselves.

**A non-string is refused, not coerced.** `String({})` is `'[object Object]'`, which parses as a
relative path and would have been **allowed** — a programming error rendering a link.

**The allow-list is context-dependent, and the context lives at the call site.** `data:` and `blob:`
are absent from the default and passed by the two *image* builders, because `data:text/html` in an
`href` is a script and the same value in an `<img src>` is an inert picture.

## Where it lands was measured, twice

Spec 09 NFR-46 said measure before choosing, and the arithmetic eliminated both obvious homes:

| Entry | Free under its clause | Guard |
|---|---:|---:|
| root | 147 B | 247 B |
| `/text` | 26 B | 247 B |

`/sanitize` had no clause figure, so its limit is a derived pin that can move — and the charter is
why it is *right* rather than merely available: `sanitizeHtml` decides which tags an untrusted string
may carry, `safeUrl` which schemes an untrusted URL may carry. The builders reach an internal module,
never the entry, so ADR-0030 is untouched.

Then the harder measurement. I built the honest version first — one function, validated everywhere —
and it put `/bootstrap` at **25 003 B against a 25 000 B clause. Three bytes over.**

| | `/bootstrap` | five per-function rows |
|---|---:|---|
| one function | 25 003 B (**3 B over**) | +371 to +396 B each |
| split parse/policy | 24 902 B | +212 to +252 B each |

My first instinct on seeing 101 B was to reject the split as not worth a second code path — and that
was judging the entry alone. The five per-function rows are what a consumer of one builder actually
pays, and there the split is worth ~750 B. So it ships, with the cost recorded rather than hidden: a
builder's own malformed `protocols` **fails closed** — it cannot widen the set, and the marker
attribute shows it — while `safeUrl` throws for the caller who calls it directly. Fail-closed *and
observable* is defensible; fail-closed and silent would not have been, which is what the marker
earns.

Even split, 98 B under a clause is not a margin to ship on — 22.1 spent a whole item establishing
that. So **ADR-0041's clause moves to 25.5 kB**, by the minimum that restores the 368 B the row
actually had. What that clause was sized to prevent is the catalogue *sprawling*; a security control
on components that already exist is not sprawl, and ADR-0079's refusal to raise it for a convenience
wrapper is exactly why raising it here is affordable.

## What F87 said, and it is the largest gap this table has shown

`url-guard.js` became its own shared chunk:

| Route | Served | Requests |
|---|---|---|
| `/sanitize` | +724 B | 3 → **4** |
| `/bootstrap` | +1 051 B | 12 → **13** |
| `/ui` | +913 B | 10 → **11** |

The same code is **247 B** on a bundler consumer's row. And `/ui` pays for a guard it never calls,
because it composes `/bootstrap` internals. One change, three routes, and only this accounting can
see the second number (ADR-0061).

NFR-22 re-derives to **71 kB** (70 546 B) — precisely as 21.5 predicted when it landed 20 B under
70 kB and said the next byte would move it.

## The gate 22.1 built, working on the next item

`check:size-figures` failed five rows immediately — `bsCard`, `bsBreadcrumb`, `bsListGroup`,
`bsCarousel`, `bsNavbar`, each +370 to +396 B — which is exactly the class of drift that went
unnoticed for a month before this morning. It also caught the ten "restated limit" contradictions
after I re-pinned. The mechanism that produced 22.1's rot could not have survived this item, and it
did not.

## A correction, carried forward

ADR-0083 and spec 09 say *eight* call sites. The eighth was `bootstrap-elements.js:387` — a line
inside a **JSDoc example**, counted by the audit's grep and never executed. Seven is the number, the
suite asserts it, and ADR-0046 set the precedent for carrying a miscount forward in the record that
found it rather than rewriting the one that made it.
