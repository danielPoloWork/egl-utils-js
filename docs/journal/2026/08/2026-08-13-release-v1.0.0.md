## Where the compatibility statement went, and why not only the release notes

The item asks for "a short compatibility statement naming the supported runtimes and what the
stability promise covers". Putting that only in `docs/releases/v1.0.0.md` would have been the
literal reading and the wrong one: a release-notes file is a dated artifact nobody re-reads, and
the promise is a standing commitment for the whole 1.x line. So it lives in three places with
different jobs:

- **README → "Stability promise"** — where a prospective consumer decides whether to depend on
  this at all.
- **`docs/workflow/maintenance.md`** — where the *maintainer* looks when deciding a SemVer level,
  slotted under the existing "What the version number protects" heading it makes concrete.
- **The release notes** — a snapshot of both, for the announcement.

All three state what is **outside** the promise as explicitly as what is inside: byte budgets (a
gate, not an API), the emitted shape of internal `.d.ts` typedefs, error message *wording* (branch
on `.code`), and what the optional peers do inside their declared ranges. A promise that only
lists what it covers invites the reader to assume the rest.

## The detail that would have shipped wrong

The 17.1 review counted **110 exports across ten entries**, and I quoted it into the release notes,
the changelog, the README and `maintenance.md` before checking. It is stale: 17.10 added
`withUrlParams` to the root and 17.12 added two error classes, so the surface is **113 exports,
102 distinct names**. Counted from the built bundles rather than trusted:

| Entry | Exports |
|---|---:|
| root | 38 |
| `/bootstrap` | 29 |
| `/dom` | 13 |
| `/errors` | 10 |
| `/net` | 6 |
| `/storage`, `/table`, `/logging` | 4 each |
| `/text` | 3 |
| `/sanitize` | 2 |

A 1.0 announcement asserting the size of its own frozen surface is exactly the wrong place for a
number carried over from three PRs ago. Corrected in all four files. The lesson is the one 17.4
taught in a different costume: a figure from an earlier document is evidence about *then*.

## Sequencing: not the two-PR dance the review predicted

The v0.1.0 review's §1.3 recorded that the consistency lint asserts the newest
`docs/changelog/vX.Y.Z.md` equals `version.js`, and concluded the release was necessarily a
two-PR sequence — bump first, prose second. That is true only if the bump happens in CI's Version
PR. **The practice since v0.2.0 has been one PR**: run `changeset version` locally, then write the
prose in the same branch, so both sides of the lockstep move together and the lint is satisfied
at every commit. Verified against the v0.9.0 release commit before choosing this shape.

## What is the owner's from here (AGENTS.md §6.1, §11)

Merging this PR **publishes nothing**. In order:

1. **Merge** this release PR.
2. **Enable Pages**, still pending from 17.3, so the release also publishes its reference:
   `gh api -X POST repos/danielPoloWork/egl-utils-js/pages -f build_type=workflow`
3. **Tag** — the agent may run `git tag -a v1.0.0` and push it once the merge lands, which makes
   `release.yml` draft the GitHub Release from `docs/releases/v1.0.0.md`.
4. **Publish the GitHub Release** (the button) — this is what triggers the docs deploy.
5. **Publish to npm** by dispatching **publish**, first with `dry-run` left checked to see exactly
   what would ship, then unchecked. Note from the v0.1.0 review: `publish.yml` has **never
   executed**, so the dry run is the real smoke test of that path.
   - One-time npm setup if not already done: a trusted publisher for `egl-utils-js` pointing at
     `.github/workflows/publish.yml` (OIDC, so there is deliberately no `NPM_TOKEN`).
