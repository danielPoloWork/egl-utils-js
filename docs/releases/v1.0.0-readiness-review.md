# v1.0.0 readiness review

- **Roadmap item:** 17.1 (the first item of Milestone 17)
- **Date:** 2026-08-09
- **Reviewed at:** `main` after PR #106 — v0.9.0, 110 exports across 10 entries
- **Verdict:** **the library is complete and every gate is green; the surface is not yet
  settled.** Seven findings would cost a **major** to fix after 1.0 and are the reason this
  review exists. None of them is a defect: the code does what it says. They are places
  where the 1.0 freeze would make a divergence permanent. **The 1.0 decision stays with the
  owner** — this document is evidence, not authorization.

The 7.6 precedent applies: findings are **filed as roadmap items, not folded in**. This
review proposes no features and changes no code.

The organising question is not "is it correct" — 2213 tests, 100% line coverage and eleven
green gates already answer that. It is narrower and only askable once: **after 1.0, which
of these could we no longer change without a major?** Everything below is sorted by that
test, because it is the only thing that makes an item urgent *now* rather than in 1.x.

## 1. The surface, measured

Resolved by importing every entry and enumerating its live bindings, not by reading the
Spec Coverage Map.

| Entry | Exports | Notes |
|---|---:|---|
| `egl-utils-js` (root) | 35 | 27 functions, 8 error classes, `VERSION` |
| `egl-utils-js/bootstrap` | 29 | 27 `bs*` builders + 2 icon sets |
| `egl-utils-js/dom` | 13 | |
| `egl-utils-js/errors` | 10 | the full taxonomy |
| `egl-utils-js/net` | 6 | |
| `egl-utils-js/storage` | 4 | 3 of them singletons |
| `egl-utils-js/table` | 4 | |
| `egl-utils-js/logging` | 4 | |
| `egl-utils-js/text` | 3 | |
| `egl-utils-js/sanitize` | 2 | |
| **Total** | **110** | **102 unique names** — the 8 root error classes are re-exports |

Behind those 110 exports sit **52 option typedefs** and **15 distinct instance shapes**.
That ratio is where the drift lives: the exports were reviewed one milestone at a time and
each is defensible on its own; the option bags and instance shapes have never been read
side by side until now.

The 27 `bs*` builders split three ways by return type — **9 return a bare `Element`**
(`bsIcon`, `bsBadge`, `bsButton`, `bsButtonGroup`, `bsCloseButton`, `bsSpinner`,
`bsPlaceholder`, `bsCard`, `bsBreadcrumb`), **3 return the shared `BehaviourWrapper`**
(`bsCollapse`, `bsDropdown`, `bsOffcanvas`), and **15 return a bespoke instance**. This is
the split the roadmap item names, and §3.1 is the answer: it is a *deliberate* split, and
it is the instance side that has diverged, not the boundary between them.

## 2. Freeze-critical findings

Fixing any of these after 1.0 costs a **major**. That is the whole claim; each is stated
with what it costs to leave, what it costs to change, and what "no change" would mean.

### 2.1 Unknown option keys are accepted in silence, everywhere

None of the 52 option bags rejects a key it does not know. Verified against the live build:

```js
bsBadge('x', { varient: 'danger', pil: true });
// → <span class="badge text-bg-secondary">x</span>   — the typo is simply gone
bsButton({ label: 'Save', autoHideMs: 3000 });
// → <button type="button" class="btn btn-primary">Save</button>
```

The second line is the shape of the real failure, and it is not hypothetical: §2.3 shows
the library uses **two different vocabularies for auto-dismiss**, so a caller who learned
`autoHideMs` from `bsAlert` and applies it to `bsToast` gets a toast that silently ignores
it and hides on Bootstrap's 5-second default instead. Nothing warns. Nothing throws. The
option surface is the largest part of this API and it currently has no spell-checker.

**Why it is freeze-critical.** Strictness cannot be added later. Code that passes an
unknown key "works" today, so a 1.x that started throwing would break consumers, and a
2.0 is exactly what the 1.0 is meant to avoid. The decision is now or never.

**The counter-argument is real and should be weighed:** silence keeps a caller's config
object forward-compatible — passing next version's option to this version degrades instead
of crashing — and every builder already validates the keys it *does* know, throwing a
`TypeError` that names the option. What is missing is only the unknown-key case. A middle
route exists (reject in development, ignore in production), and it has a cost of its own:
two behaviours to document and test.

→ filed as **17.7**.

### 2.2 `label` means two different things across sibling builders

Seven option bags define `label`. In **six** it is the accessible name:

| Export | `label` is |
|---|---|
| `bsIcon` | accessible name (its presence flips `role="img"` / `aria-hidden`) |
| `bsButtonGroup` | accessible name — **required** |
| `bsCloseButton` | accessible name, default `'Close'` |
| `bsSpinner` | visually-hidden status text, default `'Loading…'` |
| `bsProgress` | accessible name for the bar |
| `bsBreadcrumb` | the nav's accessible name, default `'breadcrumb'` |
| **`bsButton`** | **visible text** — the accessible name is `ariaLabel` |

`BsTableColumn.label` ("header content") reads the second way too. So the split is 6–2, and
the two readings sit inside one import:

```js
bsButton({ label: 'Save' });          // 'Save' is on screen
bsCloseButton({ label: 'Save' });     // 'Save' is only in the accessibility tree
```

Both are individually defensible — `label` for a button's face is the ecosystem norm, and
`label` for an accessible name is this library's own norm elsewhere. Together they are a
coin flip, and a11y options are exactly where a silent misreading does its damage.

**Why it is freeze-critical.** Renaming a public option is breaking either way it is
resolved (`bsButton({text})`, or `label`→`ariaLabel` in the other six).

→ filed as **17.8**.

### 2.3 Two vocabularies for auto-dismiss, in one entry

| API | Auto-dismiss options |
|---|---|
| `inlineAlert`, `bsAlert` | `autoHideMs` (a number; absent means never) |
| `bsToast` | `autohide` (boolean) + `delay` (number) — Bootstrap's own names |

`autohide` and `autoHideMs` differ by one capital and a suffix. Combined with §2.1 the
mistake is silent. There is a *reason* for the split — `bsToast` passes `autohide`/`delay`
straight through to Bootstrap's `Toast` config, and renaming them would put a translation
layer where a passthrough is today — but that reason is invisible at the call site.

The same question has a smaller sibling: **the `Ms` suffix convention is real but partial.**
`autoHideMs`, `minVisibleMs`, `debounceMs` carry the unit; `delay`, `interval`, `timeout`,
`maxWait` do not, and are also milliseconds. The root's own `delay(ms)`, `debounce(fn,
delay)` and `throttle(fn, interval)` set the unsuffixed precedent, so this is a convention
with two halves and no written rule.

→ filed as **17.8**.

### 2.4 `update()` means three different things, and the table calls it `setData()`

| Method | What it does | Argument |
|---|---|---|
| `bsListGroup(...).update` | re-render from new data | `items` |
| `bsPagination(...).update` | re-render from new data | `{page, pageCount}` |
| `bsProgress(...).update` | re-render from new data | `value` (a number) |
| `bsTooltip/bsPopover(...).update` | **reposition** — Popper's `update` | *(none)* |
| `bsTable(...).setData` | re-render from new data | `rows` |
| `bsNavbar(...).dropdowns[n].update` | reposition | *(none)* |

Three of the six re-render, two reposition, and the largest data component in the library
opts out of the name entirely. A caller who has learned `update` on a list group and reaches
for it on a table finds nothing; a caller who reaches for it on a tooltip finds something
that does an unrelated thing successfully.

The reposition sense is inherited (Bootstrap and Popper both call it `update`), which is a
good argument for keeping it and renaming the *data* sense — the opposite of what one would
guess from the 3-vs-2 count.

→ filed as **17.8**.

### 2.5 `show()` returns three different things

| `show()` on | Returns |
|---|---|
| `BehaviourWrapper` (`bsCollapse`/`bsDropdown`/`bsOffcanvas`), `bsModal`, `bsTooltip`/`bsPopover`, `inlineAlert`/`bsAlert` | `void` |
| `bsToast` | the toast `Element` it just built |
| `loadingOverlay`/`bsLoadingOverlay` | `() => void` — a **release handle** |

Each is right locally: the toast manager builds a fresh node per call so returning it is the
only way to reach it, and the overlay is reference-counted so a release handle is the whole
contract. But `const x = thing.show()` is the same expression in all three, and `x` is a
node, a function, or `undefined` depending on which import it came from.

→ filed as **17.9**.

### 2.6 Use-after-`destroy()` is specified by convention, and one component breaks it

Probed against the live build after calling `destroy()`:

| Call after `destroy()` | Result |
|---|---|
| `bsListGroup(...).update(...)` | `TypeError: bsListGroup: update() was called after destroy()` |
| `bsPagination(...).update(...)` | `TypeError: bsPagination: update() was called after destroy()` |
| `bsAlert(...).show(...)` | `TypeError: inlineAlert: show() was called after destroy()` |
| `bsTable(...).setData(...)` | `TypeError: bsTable: setData() was called after destroy()` |
| **`bsProgress(...).update(50)`** | **succeeds, silently, on a detached node** |

Four of five instances fail loudly and name the API. `bsProgress` is the exception because
its whole teardown is `() => track.remove()` — there is no destroyed flag to check. A
progress bar that keeps accepting updates after teardown is the classic "the UI stopped
moving and nothing was logged" bug.

Two smaller things ride along:

- **The error is a `TypeError`, not an `EglError`.** A state violation has no `EGL_*` code,
  so the one branch a consumer is told to write (`err.code === 'EGL_…'`, ADR-0003) does not
  reach it. That is consistent across the library — argument validation is a `TypeError`
  everywhere, ~280 throw sites — but the boundary between "typed failure with a code" and
  "platform error" is nowhere written down, and 1.0 freezes the code registry (ADR-0003).
- **`bsAlert`'s failure names `inlineAlert`.** Composition leaks the engine's name into the
  public API's diagnostics (ADR-0038 makes the composition deliberate; the message
  attribution is an unintended consequence).

→ filed as **17.9**.

### 2.7 `withUrlParams` is a pure URL helper frozen onto the DOM entry

`withUrlParams(url, params)` lives on `egl-utils-js/dom` and its own JSDoc is explicit:
*"Pure and SSR-safe: it never touches `document`, `location`, or the `URL` constructor."*
Meanwhile `urlSearchParams(params)` sits on the root, and the two share a contract — the
JSDoc says so: nullish values are skipped, arrays repeat the key.

So the one function on `/dom` that has no DOM dependency is on the entry that exists to
fence DOM code off, and its sibling is one import away on the root. A Node consumer who
wants it must import from `/dom`.

It arrived there legitimately (spec 03 F48 placed it with the DOM wave). **Moving an export
between entries after 1.0 is breaking**, so this is the last cheap moment — and the cheap
fix is additive: re-export it from the root and deprecate the `/dom` binding.

→ filed as **17.10**.

### 2.8 The `dompurify` peer range admits known-vulnerable versions

`peerDependencies.dompurify` is `^3`. As of this review:

- **GHSA-55q2-fjhq-7xh7** (moderate) affects `dompurify <= 3.4.12`; patched in `3.4.13`.
- This repository's own devDependency resolves to **exactly 3.4.12** — the last vulnerable
  version — so the browser suite and the sanitize tests run against it today.
- `pnpm audit --audit-level high` **passes**, because the advisory is moderate. The gate is
  working as configured; the configuration is what this finding is about.

**The library itself is not exposed by this specific advisory.** It concerns DOMPurify's
`IN_PLACE` mode, and `sanitizeHtml` pins `IN_PLACE: false`, `RETURN_DOM: false`,
`RETURN_DOM_FRAGMENT: false` explicitly. That is worth stating plainly rather than implying
a vulnerability the code does not have.

What the finding *is*: a 1.0 freezes `^3` as the declared compatible range for the peer of
the **security** entry, and half of that range is known-vulnerable. Narrowing a peer range
afterwards is a breaking change for anyone inside the part being removed.

Two dev-only advisories accompany it, both build-time and neither shipped: `postcss`
`<=8.5.22` (moderate, via `tsup`) and `esbuild` (low, dev-server only, via `tsup`).

→ filed as **17.11**.

## 3. Additive findings — recorded, not blocking

These are real, and none of them is urgent, because **adding an export or a method is a
MINOR**. They are listed so the 1.0 does not ship on the belief that the surface is uniform.

### 3.1 The instance member matrix

Across the 15 instance shapes:

| Member | Present on | Absent from |
|---|---:|---|
| `destroy()` | **15/15** | — |
| `element` | 12/15 | `bsToast`, `inlineAlert`/`bsAlert`, `loadingOverlay`/`bsLoadingOverlay` |
| `on(event, handler)` | 7/15 | incl. `bsToast`, `bsListGroup`, `bsProgress`, `bsTable` |
| `instance()` (Bootstrap escape hatch) | 5/15 | incl. `bsToast`, `bsTabs`, `bsAccordion`, `bsNavbar` |
| `isShown()` | 2/15 | **incl. `bsModal`** |

`destroy()` being universal is the important result: the lifetime contract *is* uniform, and
that is the one that would have been expensive to get wrong.

The rest is patchy for defensible reasons — a list group has no Bootstrap component to
escape to, a scrollspy has no open state — but two gaps are hard to justify from the
outside. **`bsModal` has no `isShown()`** while `bsOffcanvas`, its sibling overlay, does
(it is a `BehaviourWrapper`); the modal is the component most likely to be asked whether it
is open. And **`bsToast` has neither `on()` nor `instance()` nor `element`**, so the manager
exposes no route to Bootstrap's toast events at all — mitigated, but only because `show()`
returns the node, which the caller can attach to itself.

### 3.2 The root re-exports 8 of the 10 error classes — contradicting ADR-0003

`egl-utils-js/errors` exports 10 classes. The root re-exports 8. Missing:
**`DomContractError`** (`EGL_DOM_CONTRACT`) and **`PeerMissingError`** (`EGL_PEER_MISSING`)
— the two added after M8, by the `/dom` and `/bootstrap` waves.

ADR-0003 states the taxonomy is *"exported from `egl-utils-js/errors` and re-exported from
the root entry"*, and `index.js`'s own module comment repeats it: *"importable from the root
and from `egl-utils-js/errors` alike"*. Both are now false. The practical effect is small —
`err.code` works regardless, which is the documented idiom — but a documented contract that
the code stopped satisfying is precisely what a readiness review is for.

Fixing it is additive. The only question a 1.0 has to answer is whether the ADR-0003 clause
should be honoured or amended (a DOM error class on a Node-safe root is a fair objection).

### 3.3 Three exported singletons are mutable; four exported constants are frozen

`Object.isFrozen` over the exported non-function values:

| Export | Frozen |
|---|---|
| `LOG_LEVELS`, `defaultSanitizeProfile` (and its arrays), `bootstrapIconsSet`, `materialIconsSet` | ✅ |
| `localStorageWrapper`, `sessionStorageWrapper`, `cookieHelper` | ❌ |

The storage wrappers are method bags, so freezing them prevents a consumer from
monkey-patching `localStorageWrapper.get` for the whole process. Freezing is additive and
cheap; the reason to think about it before 1.0 is that *someone may already be doing it*,
which makes freezing breaking in the other direction. A deliberate decision either way.

Naming is a smaller version of the same: `LOG_LEVELS` is the only `SCREAMING_SNAKE` export
in 110; `defaultSanitizeProfile`, `bootstrapIconsSet` and `materialIconsSet` are camelCase
constants of the same kind. Renaming is breaking; it is listed here so it is a choice.

### 3.4 Spec 01 §5 no longer enumerates the surface it names

Spec 01 §5 lists **23 root exports** and **7 error classes**. Today the root has 35 and the
taxonomy has 10. The additions all arrived legitimately under specs 02–04 (which own their
own §5 sections), and the consistency lint checks the *coverage map*, not these
enumerations — so nothing has flagged it for three milestones.

For a 1.0 whose headline promise is a frozen public interface, the spec section named
"Public Interface" ought to either match, or say explicitly that it covers F1–F25 only and
delegates the rest. Once 17.3 publishes the generated API reference there is also a third
option: point at that and stop maintaining the list by hand.

## 4. Checked, and found sound

Negative results are part of the evidence. Each of these was examined for the same
"would we regret freezing it" question and passed.

- **The exports map.** 10 entries plus `./package.json`, `types` first in every condition,
  `import`/`require` for all, the extra `node` condition only on the root (where the
  `#webcrypto` split needs it, ADR-0008). `publint --strict` and `attw --profile node16`
  both pass. The shape is what a 1.0 should freeze.
- **The error-code registry.** 10 classes, 10 distinct `EGL_*` codes, no collisions, no
  orphans; every class carries `name` and `code` as own fields, so cross-realm identity by
  `code` works as ADR-0003 promises. Payload constructors are uniform: `(message, details?)`.
- **`signal` is genuinely universal.** It appears in 25 option bags and always means the
  same thing — abort tears the thing down. Not one variant spells it differently or gives it
  a second meaning. This is the strongest consistency result in the review.
- **The `{html, sanitize}` gate.** 15 bags take `html`, 16 take `sanitize`, and the pairing
  rule (`html: true` without `sanitize` is a `TypeError`) holds everywhere — including at
  the per-column level in `bsTable`, which overrides the table-level default without
  escaping the gate.
- **First-parameter naming.** `container` where the builder fills it, `target` where it
  attaches to what is already there, `toggler` for the one dropdown case. A real convention,
  followed by all 15 attaching builders.
- **Callback argument order.** Data-carrying callbacks put the event last
  (`onSelect(item, index, event)`, `onRowClick(row, event)`); `delegate`'s handler puts it
  first (`(event, matchedElement)`), which is the DOM-primitive idiom and reads correctly
  in context. Two rules, each internally consistent — worth *writing down* in 17.8, not
  worth changing.
- **Size and shakeability.** All 27 `size-limit` rows pass, `agadoo` confirms the ESM entry
  is side-effect free, and `assert-no-runtime-deps` confirms zero runtime dependencies.
- **`VERSION`** is on the root (ADR-0018), in lockstep with `package.json` and the README
  badge (`sync-version --check` passes).

Also checked and deliberately **not** re-litigated: `/sanitize`'s static `dompurify` import
versus `/bootstrap`'s lazy peer lookup. That contradiction is already **17.6**, filed by the
M17 planning PR before this review ran. It would otherwise have been this review's first
finding.

## 5. What this review did not cover

Stated so the verdict is not read wider than it is:

- **No new capability was assessed.** The item forbids proposing features, and none is
  proposed.
- **The runtime floor (17.2) and the NFR-01 clause (17.4)** are separate items with their
  own decisions; this review did not pre-empt either.
- **Behavioural correctness** was taken from the suite (2213 tests, 100% lines) rather than
  re-derived. This is an API-shape review.
- **`coverage.thresholds` gates lines and branches only.** Functions sit at 98.89% and
  statements are ungated. Both are far above any plausible bar — noted, not filed.

## 8. Recommendation

**The content of a 1.0 is ready. The shape of it needs six decisions first.**

Nothing found here is a defect, and nothing blocks the *library*. What §2 establishes is
that seven divergences currently sit inside a surface about to become MAJOR-protected, and
that six of them are cheap now and expensive later. That asymmetry — not risk, not
incompleteness — is the argument for taking 17.7–17.11 before 17.5.

Suggested order: **17.7 → 17.8 → 17.9** (the three that rename or tighten public shapes,
largest blast radius first, so the later ones settle onto a fixed vocabulary), then
**17.2** (the runtime floor, whose api-floor churn is independent), then **17.10, 17.11,
17.12** (small and unentangled), **17.4** and **17.6** in any order, **17.3** whenever, and
**17.5** last.

If the owner prefers to ship 1.0 sooner, the defensible minimum is **17.7 and 17.8**: the
option-key contract and the naming vocabulary are the two that a consumer meets on their
first call and that a major boundary makes permanent. §2.5–§2.8 could then be accepted as
recorded 1.0 behaviour with the reasons written down — which is itself a legitimate answer,
provided it is a decision and not an oversight. That is what this document exists to
prevent.
