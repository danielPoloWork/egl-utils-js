# egl-utils-js v1.4.0

**A form is a subsystem, and it now has one.**

```bash
npm install egl-utils-js@1.4.0
```

```js
import {
  createForm,
  createValidator,
  bindFormFeedback,
  bindSubmit,
  trackChanges,
} from 'egl-utils-js/forms';
import { BOOTSTRAP_FEEDBACK_CLASSES } from 'egl-utils-js/bootstrap';

const form = createForm(root); // values, coercions, a baseline that is what you LOADED
const validator = createValidator(form, { rules, validateOn: ['blur'] });
const feedback = bindFormFeedback(validator, { classes: BOOTSTRAP_FEEDBACK_CLASSES });
const changes = trackChanges(form, { guard: true });

bindSubmit(validator, {
  feedback,
  disable: ['[type=submit]'],
  handler: ({ form, signal }) => api.put(`/hosts/${id}`, form.toJSON(), { signal }),
});
// The form's own submit button now validates, refuses on error, marks the form
// busy, disables what you nominated, awaits your handler, restores exactly what
// it took — and puts the server's field errors under the right controls.
```

Milestone 21 delivers spec 08 (F112–F125) on a new entry, `egl-utils-js/forms`. **Purely
additive**: v1.3.0's 133 exports are untouched — this release adds **seven exports, one instance
method and one new entry**, renames no `EGL_*` code, and leaves the existing `exports` map paths
byte-identical. If you use this package today, nothing you wrote stops working.

## Five pieces, and each one takes the one before it

There is no `Form` god object. `createForm` owns values; everything else is a factory that
**takes** a form or a validator, the way `bindTableControls` takes a pipeline. That is not a
style choice — it is what makes the entry payable in parts:

| You import | You link |
|---|---|
| `createForm` | 1 888 B |
| `bindFormFeedback` | 2 237 B |
| `bindSubmit` | 1 912 B |
| `trackChanges` | 1 608 B |
| the whole entry | 7 844 B |

A filter form that wants values and neither validation nor submission pays the first row.

## The coercions are the contract

These are the four bugs every hand-rolled `form.elements` loop rewrites, so they are pinned by a
property test rather than by prose:

```js
form.getValues();
// unchecked checkbox      -> false          (not undefined)
// empty <input type=number> -> null         (not NaN, not '')
// radio group, none chosen  -> null         (not '')
// <select multiple>         -> []           (always an array)
```

And **`reset()` is not `HTMLFormElement.reset()`**: the platform restores what the *markup*
shipped with, which for a record you fetched into a form means an empty form. Here the baseline is
what was loaded, `setBaseline()` adopts a new one after a save, and `reset()` restores that.

## Validation that does not fight the platform

`required` and `type="email"` stay in the markup, where a no-JavaScript submit still honours them,
and their failures arrive as findings in the same shape as your rules'. A field's own error is
pushed back through `setCustomValidity`, so `checkValidity()` and this engine can never disagree.

**Only `error` blocks.** `warning` and `info` are reported and never gate a submit — and because
`valid` is `true` before anything has run, the result also carries `validated`, so "passed" and
"not asked yet" stay distinguishable.

**Latest-wins is keyed per rule, not per run.** A cross-field rule declares `dependsOn`, so one
run can write another field's findings — which means two concurrent runs could collide. Each rule
owns at most one in-flight execution, the loser is aborted, and staleness is checked by *identity*
because an `AbortSignal` cannot un-resolve a promise that already settled.

## A submit that cannot double-submit

```js
const first = submitter.submit();
const second = submitter.submit();
second === first; // true — the same promise, not a refusal and not a second request
```

A boolean `busy` flag checked at the top of an `async` function is the same bug with more code:
the check and the set are separated by an `await`. So the guard *is* the promise, which is also
why `submit()` is deliberately not an `async` method.

**A blocked submit is an answer; a failed one is a failure.** Validation finding an `error`
resolves with `{status: 'blocked'}`. Your handler rejecting rejects `submit()` with **your own
error object** — an `HttpError` arrives with its `status` and `body` intact, because re-wrapping
it would cost you the two things you need.

## Your server's errors, on the right fields — safely

This is the first place this library routes bytes it did not receive from you onto the DOM, so
the rules are explicit rather than implicit:

```js
// 422 { errors: { email: 'Already registered', legacy_flag: 'No longer accepted' } }
//   -> `email` renders under the email control and blocks the next submit
//   -> `legacy_flag` matches no control, so it renders at form level carrying `field`
//      — silently discarding a server's complaint is how a user is told "something
//        went wrong" with no idea what
```

- a field name from the server is **matched** against the fields your form resolved, **never used
  as a selector** — a name like `input[name=email]` selects nothing;
- every message reaches the DOM as **text**, through a renderer that deliberately has no
  `{html, sanitize}` opt-in;
- the default mapper builds its field map through `Object.fromEntries`, so
  `{errors: {__proto__: …}}` cannot reach `Object.prototype`.

The boundary and its full STRIDE pass are in
[`docs/security/threat-model.md`](../security/threat-model.md), shipped in the same PR as the
code.

## Dirty is not touched

```js
type('name', 'Grace'); // dirty, touched
type('name', 'Ada'); // clean, still touched
```

An undo is not a visit that never happened. A guard wants the first fact; "do not show me an error
for a field I have not filled in yet" wants the second. **Dirty is derived on every read**, never
stored, because the baseline moves under it — a cached flag would tell a user they have unsaved
changes to a record they just saved.

The `beforeunload` guard is **opt-in and attached only while the form is dirty**: a live
registration costs the page its back/forward-cache eligibility in every current engine. And
because the browser's own dialog is not yours to word — several engines skip it entirely without
prior interaction — `confirmLeave()` covers the in-app route change `beforeunload` never sees, in
your own words:

```js
const changes = trackChanges(form, {
  guard: true,
  confirm: ({ dirtyFields }) => dialogs.confirm(`Discard ${dirtyFields.length} change(s)?`),
});

router.beforeEach(async () => await changes.confirmLeave());
```

## Compatibility

- **Additive only.** 133 exports become 140 across twelve entries; the eleven existing entries and
  every path in the `exports` map are unchanged.
- **One widened union**: `Finding.source` gains `'external'` and `Finding` an optional `field`. A
  consumer exhaustively switching on `source` sees a case it did not before — classified as a
  minor addition, and called out rather than assumed.
- **Runtime floor unchanged**: Node.js >= 22, Safari >= 16.4. One new platform API is used
  (`Window.beforeunload`, behind an opt-in), inventoried against that matrix like the other 57.
- **Zero runtime dependencies**, unchanged. `bootstrap` and `dompurify` remain optional peers, and
  `/forms` needs neither.
